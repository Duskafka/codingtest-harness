# S03. 문제 식별 파서

| 항목 | 내용 |
|---|---|
| 단계 | P1 |
| 선행 | S01 |
| 결정 게이트 | 없음 |
| 사람 할 일 | H-01 (실제 커밋 샘플). 없으면 백준허브 공개 소스를 기준으로 만들고 '추측'으로 표시 |
| T번호 | 없음 (샘플 기반 파서 테스트) |

## 목표

커밋 메시지와 파일 경로를 보고 어떤 플랫폼의 몇 번 문제인지 알아내는 순수 함수를 만든다.

## 읽을 문서

- `docs/spec/processes/5.04-problem-identification.md` 전체
- `docs/spec/external-systems.md`: 백준허브 행, [S41]
- `docs/spec/glossary.md`: `ProblemRef`, `Platform`

## 만들 것

1. **파서 (`verification` 모듈):** DB를 모르는 순수 함수. 5.4의 모양은 `parse(commitMessage, paths) → List<ProblemRef>`다.
    - 5.4 흐름도의 '확인 대기'는 연결할 때 지정한 경로 접두사가 필요하다. 파서가 접두사를 받을지, 결과로 '식별 못 한 파일'을 돌려주고 호출하는 쪽(S08)이 판단할지 정해서 판단 기록에 남긴다.
2. **경로 정규화:** 유니코드 NFC, 전각 문자.
3. **식별 규칙:** 경로 규칙 → 메시지 규칙 순서 (5.4 흐름도). 같은 커밋의 여러 파일은 문제당 하나로 합친다.
4. **플랫폼 값:** 백준, 프로그래머스, LeetCode. `Platform`의 실제 값을 정한다.
5. **파서 버전:** 상수로 둔다. S08이 풀이 기록에 남긴다.
6. **샘플 테스트:** `src/test/resources/commit-samples/`의 샘플을 읽어 도는 테스트. 샘플 파일 형식(메시지, 경로 목록, 기대 결과)을 그 폴더의 README에 적어서 사람이 샘플을 더하면 테스트가 늘어나게 한다.

## 만들지 않을 것

- push payload 처리, 풀이 기록 저장 (S08)
- 코드트리 GitHub 연동 형식 (5.4 표에서 '확인 필요'). 샘플이 생기면 그때 더한다

## 수용 기준

- [ ] 백준허브의 백준 형식 커밋 → (백준, 번호)
- [ ] 백준허브의 프로그래머스 형식 커밋 → (프로그래머스, 번호)
- [ ] 경로에 전각 문자(＋, ［ ］)가 있어도 번호로 식별한다. 제목은 비교에 쓰지 않는다
- [ ] NFD로 온 한글 경로도 식별한다
- [ ] 한 커밋에 같은 문제의 파일이 여러 개면 결과는 하나다
- [ ] README만 고친 커밋 → 결과 없음
- [ ] 백준 1000번과 프로그래머스 1000번은 다른 `ProblemRef`다
- [ ] LeetCode 확장 형식은 샘플이 있으면 식별하고, 없으면 테스트를 '추측' 표시와 함께 둔다

## 주의할 것

- 재개된 백준에서 백준허브 형식이 바뀔 수 있다. 샘플이 사람이 준 실제 커밋인지, 공개 소스에서 만든 것인지 샘플 파일에 표시한다.
- 5.4의 '알려진 형식' 표는 예시다. 실제 샘플이 표와 다르면 샘플을 따르고 PR의 '스펙 변경 제안'에 적는다.

## 판단 기록이 필요한 곳

- 파서 입출력 모양 (위 1번)
- `Platform` 값 이름
- 샘플을 공개 소스에서 만들었다면 그 출처 링크와 '추측' 표시
