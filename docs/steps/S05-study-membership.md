## 목표

방장이 1분 안에 스터디를 만들고, 멤버는 링크 하나로 들어온다. 이후 모든 권한 검사가 기대는 `StudyAccess`를 만든다.

## 만들 것

1. **스터디 만들기:** 규칙 1번 버전(`effective_from` = 시작일), 1기 기수, 방장 멤버십을 한 트랜잭션으로 저장한다. 규칙 마법사 기본값은 R1 표.
2. **목록과 상세:** `GET /api/studies`, `GET /api/studies/{id}` (현재 규칙, 기수).
3. **이름 변경과 방장 위임:** `PATCH /api/studies/{id}`.
4. **규칙 변경:** `PUT /api/studies/{id}/rules`. 다음 스터디 일부터 적용하는 새 버전을 만들고, 과거 판정에는 소급하지 않는다 (R2). OD-08이 정해지기 전에는 만들지 않는다.
5. **초대:** 32바이트 무작위 토큰(base64url), SHA-256 해시만 저장, 기본 7일 만료, 철회, 사용 횟수 제한. `POST /api/studies/{id}/invitations`, `GET /api/invitations/{token}` (공개, 규칙 요약), `POST /api/invitations/{token}/accept`.
6. **수락:** 같은 사람이 두 번 눌러도 결과가 같다. 정원 30명. `judged_from` = 가입 다음 스터디 일 (R14).
7. **스터디 탈퇴:** `DELETE /api/studies/{id}/members/me`. `left_at` 기록, 그날까지 판정. 방장은 위임한 뒤에만 탈퇴할 수 있다.
8. **혼자 쓰기 모드:** 멤버 1명, 초대 기능 없음, 벌금 방식 기본값 '없음' (R15).
9. **`StudyAccess`:** 멤버·방장 검사를 한 곳에 모으고 이 단계의 모든 API에 적용한다. 조회 쿼리도 스터디 ID로 범위를 묶는다.

## 만들지 않을 것

- 기수 자동 연장 (S12)
- 규칙 변경 알림 `RULE_CHANGED` (S13)
- 멤버 내보내기 (P2)

## 수용 기준

- [ ] 스터디를 만들면 규칙 v1, 1기, 방장 멤버십이 함께 생기고, 하나라도 실패하면 아무것도 남지 않는다
- [ ] T20: 만료된 토큰, 철회된 토큰, 사용 횟수를 넘긴 토큰으로 수락하면 거절된다
- [ ] T20: 마지막 한 자리를 두 명이 동시에 수락하면 한 명만 성공하고 정원을 넘지 않는다
- [ ] 같은 사람이 같은 초대를 두 번 수락하면 두 번 다 성공 응답이고 멤버십은 하나다
- [ ] 탈퇴한 사람이 다시 가입할 수 있다 (부분 UNIQUE)
- [ ] 11/20에 가입하면 `judged_from`은 11/21이다 (기준 시각 반영)
- [ ] 방장은 위임 전에 탈퇴할 수 없다
- [ ] DB에 초대 토큰 원문이 없다
- [ ] T11 (규칙 변경이 열려 있을 때): 규칙을 바꾸면 새 버전의 `effective_from`은 다음 스터디 일이고, 그 전 날의 규칙은 바뀌지 않는다
- [ ] T19: 이 단계의 모든 엔드포인트에서 다른 스터디의 ID로 요청하면 403 또는 404다
- [ ] 혼자 쓰기 스터디에서는 초대를 만들 수 없다

## 주의할 것

- 정원 동시성: `UPDATE invitations SET used_count = used_count + 1 WHERE id = ? AND used_count < max_uses`의 영향받은 행 수로 판단한다 (5.1).
- 스터디 시간대는 만들 때 정하고 바꾸지 않는다 (5.1).
- 가입 전에 규칙 요약을 보여 줘야 한다. 미리보기 응답에 규칙 요약을 담는다.

## 판단 기록이 필요한 곳

- 기수의 끝 날짜 계산 방식 (기수 길이, OD-07 전에는 1기만)
- 미리보기에 담는 규칙 요약 항목 (공개 엔드포인트라 노출 정보를 최소로)
- 응답 본문 모양 (프론트가 쓸 계약이라 '꼭 봐 주세요')
