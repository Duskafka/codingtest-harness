# 작업 방식

이 레포는 하네스 방식으로 만들어요. 에이전트(Claude Code 클라우드 세션)가 단계 하나씩 구현하고 판단을 기록하면, 사람이 그 기록을 읽고 검토하고 결정해요.

## 1. 역할

| 누가 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 에이전트 | 단계 구현과 테스트, 판단 기록, 결정 제안서, 인계 기록 | 열린 결정 정하기, 스펙 수정, master 직접 push, 비밀값 다루기 |
| 검토 서브에이전트 (`spec-reviewer`) | PR 전에 diff를 단계 문서·스펙과 대조 | 코드 수정 |
| 사람 | 열린 결정, PR 검토와 병합, 스펙 수정, 외부 계정·서버·키 | — |

## 2. 세션 하나의 흐름

1. **시작 확인**
    - `docs/progress.md`의 최근 기록, `git log --oneline -15`, `docs/steps/README.md`의 상태 표를 읽는다.
    - 열린 PR을 확인한다. 세션의 GitHub 도구나 `gh api repos/Duskafka/codingtest-harness/pulls`(REST)를 쓴다. 클라우드 세션의 프록시는 GraphQL을 쓰는 `gh pr`, `gh issue`를 막는다.
    - 이어서 할 PR이 있으면 그 브랜치에서 이어 한다. 사람이 지정한 단계가 없으면 선행 단계가 모두 '완료'이고 열린 PR이 없는 첫 '대기' 단계를 고른다.
    - 단계 문서의 '결정 게이트'를 `docs/decisions/README.md`와 대조한다. 열린 결정이 있으면 3장으로 간다.
    - `./gradlew build`가 통과하는지 본다. 실패하면 그것부터 고치고, 그 PR에는 다른 일을 섞지 않는다.
2. **계획:** 단계 문서의 '읽을 문서'를 읽는다. 만들 것과 테스트 목록을 정리해 Draft PR 본문에 적는다.
3. **테스트 먼저:** 수용 기준을 테스트로 옮기고, 실패하는 걸 확인한다.
4. **구현:** 작게 커밋한다. 커밋 본문에 '왜'를 적는다.
5. **검증:** `./gradlew build`가 통과한다. `spec-reviewer` 서브에이전트에게 diff 검토를 맡기고, 지적마다 반영했는지, 반영하지 않았다면 왜인지 PR에 적는다.
6. **마무리:** PR 본문을 다 채우고 Ready로 바꾼다. `docs/steps/README.md`의 단계 상태를 바꾸고(끝났으면 '완료', 남았으면 '진행 중'), `docs/progress.md`에 인계 기록을 더한다.

한 세션에 단계 하나만 해요. 세션 안에 끝나지 않으면 거기까지 커밋·푸시하고, 인계 기록에 남은 일을 적어요. 다음 세션이 같은 브랜치에서 이어 해요.

**리뷰 반영 세션.** 사람이 PR에 리뷰를 남기면 다음 세션에서 반영해요.

1. PR 브랜치로 바꾸고, 리뷰와 코멘트를 읽는다 (`gh api repos/Duskafka/codingtest-harness/pulls/<번호>/reviews`, `.../pulls/<번호>/comments`, `.../issues/<번호>/comments`).
2. 코멘트마다 반영하거나, 반영하지 않는다면 이유를 그 코멘트에 답한다. 리뷰가 결정 제안서의 결정을 바꿨다면 그 결정대로 구현을 고친다.
3. 결정 제안서의 '결정'과 '검토 메모' 칸은 사람이 쓴다. 에이전트는 비워 둔다.
4. 다시 `./gradlew build`, 필요하면 `spec-reviewer`, 그리고 인계 기록.

## 3. 판단 기록과 결정 게이트

판단은 크기에 따라 기록하는 곳이 달라요.

| 크기 | 예 | 기록하는 곳 | 정하는 사람 |
|---|---|---|---|
| 작음: 되돌리기 쉽고 그 PR 안에서 끝남 | 클래스·메서드 이름, 쿼리 작성 방식, 테스트 구성 | PR 본문 '판단 기록' | 에이전트가 정하고, 사람이 검토 |
| 큼: 되돌리기 어렵거나 여러 단계에 영향 | 모듈 경계 해석, 테이블 구조, 라이브러리 선택, 동시성 전략 | 결정 제안서 `docs/decisions/NNN-제목.md` | 에이전트가 제안하고, 사람이 결정 |
| 열린 결정 (OD) | `docs/decisions/README.md`의 표 | 결정 제안서 (준비 담당이 에이전트일 때) | 사람 |

API 응답 모양은 프론트가 쓰는 계약이라 PR 판단 기록에 '꼭 봐 주세요'로 남겨요. 결정 제안서까지는 쓰지 않아요.

**큰 판단은 이렇게 해요.** 결정 제안서를 `docs/decisions/000-template.md`를 복사해 쓰고 (번호는 그 폴더와 열린 PR에서 가장 큰 번호 + 1), 추천안대로 구현한 뒤 같은 PR에 넣어요. 사람이 PR을 검토하면서 결정 제안서의 '결정' 칸을 채워요. 추천안이 틀렸으면 고쳐서 다시 올려요. 단, 테이블이나 컬럼을 지우거나 이미 쌓인 데이터를 바꾸는 것처럼 되돌리기가 특히 어려운 판단은 구현하기 전에 제안서만 먼저 올리고 멈춰요.

**열린 결정에 걸리면 이렇게 해요.**

1. 걸린 부분은 구현하지 않아요. 같은 단계에서 걸리지 않은 부분은 진행해도 돼요.
2. 준비 담당이 '에이전트'면 결정 제안서를 써서 docs만 바꾸는 PR로 올려요. '사람'이면 PR 본문의 '열린 질문'에 무엇 때문에 막혔는지 적어요.
3. 인계 기록에 '결정 대기: OD-NN'을 남기고 멈춰요.

**판단 기록 양식 (PR 본문)**

```markdown
### (판단 제목)
- 결정:
- 이유:
- 버린 선택지:
- 근거: 공식 문서 링크(버전), 스펙 절 번호
- 되돌리는 비용: 낮음 / 중간 / 높음
- 검토 요청: 꼭 봐 주세요 / 참고만
```

## 4. 스펙과 구현이 다를 때

- 스펙(`docs/spec/`)은 계약이에요. 구현이 스펙과 다르면 구현을 고쳐요.
- 스펙이 틀렸거나 비어 있다고 판단되면 스펙을 고치지 말고, PR 본문의 '스펙 변경 제안'에 어디를, 왜, 어떻게 바꾸자는지 적어요. 그동안 그 부분은 만들지 않거나, 되돌리기 쉬운 쪽으로 만들고 '추측'으로 표시해요.
- 스펙끼리 부딪히면 이 순서로 따라요: `domain-rules` → `data-model`·`api` → `processes` → `pseudocode`. 모듈 의존 규칙(`architecture` 4.2)은 ArchUnit이 강제하니 언제나 지켜요.
- 이미 알려진 충돌은 `docs/spec/architecture.md`의 '알려진 충돌과 빈 곳'에 있어요.

## 5. 브랜치, 커밋, PR

- **브랜치:** `<타입>/S<번호>-<짧은-설명>` (예: `feat/S09-study-day-assignment`)
- **커밋 메시지:** Conventional Commits `<타입>(<범위>): <무엇을>`. 본문에 이유를 적어요.
    - 타입: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`
    - 범위: 모듈 이름(`auth`, `study`, `github`, `verification`, `progress`, `judgment`, `ledger`, `appeal`, `notification`, `discord`, `common`) 또는 `infra`, `frontend`, `harness`
- **PR:** 단계 하나에 PR 하나. 제목은 `<타입>(<범위>): S<번호> <단계 이름>`. 본문은 `.github/PULL_REQUEST_TEMPLATE.md`를 채워요.
- **병합:** 사람이 해요. squash 병합이 기본이에요.

## 6. 완료 기준 (모든 단계 공통)

- [ ] 단계 문서의 수용 기준이 모두 테스트로 있고 통과한다 (T번호는 테스트 이름에)
- [ ] `./gradlew build`가 통과한다 (ArchUnit 포함)
- [ ] 새 엔드포인트마다 다른 스터디의 데이터에 접근하지 못하는 테스트(T19)가 있다
- [ ] DB 변경은 새 Flyway 마이그레이션으로만 했다. master에 있는 마이그레이션은 고치지 않았다
- [ ] 시간은 주입된 `Clock`으로만 다뤘다
- [ ] 비밀값, 실제 접속 정보, 개인정보가 코드·설정·로그·테스트 데이터에 없다
- [ ] 라이브러리를 더했다면 Boot 4 지원 버전인지 확인하고 근거를 PR에 적었다
- [ ] `spec-reviewer` 검토를 받았고, 지적별 처리를 PR에 적었다
- [ ] PR 본문의 판단 기록, 열린 질문, 추측한 것, 스펙 변경 제안을 채웠다 (없으면 '없음')
- [ ] 단계 상태와 `docs/progress.md`를 갱신했다

## 7. 인계 기록 (`docs/progress.md`)

세션을 끝내기 전에 맨 위에 더해요. 10줄 안쪽으로 써요.

```markdown
## 2026-12-01 S02 시간 계산 (세션 1/2)
- 한 일:
- 상태: 빌드 통과 / 실패 (이유)
- 다음:
- 막힌 것: 없음 / 결정 대기 OD-NN / 사람 할 일 H-NN
- PR: #
```

기록이 15개를 넘으면 오래된 것부터 한 줄 요약으로 줄여요.

## 8. 환경 준비 (클라우드 세션)

- **JDK 25:** 클라우드 기본 이미지에는 JDK 21만 있어요. 클라우드 환경의 설정 스크립트가 JDK 25를 설치해요 (사람 할 일 H-09).
- **Docker 데몬:** 세션마다 켜야 해요. SessionStart 훅(`.claude/hooks/session-start.sh`)이 `scripts/cloud-session-setup.sh`가 있으면 실행해요. 이 스크립트는 S01에서 만들어요.
- Testcontainers가 Docker에 붙지 못하면 `docker info`로 확인하고, 해결한 방법을 인계 기록에 남겨요.
- 훅은 단일 레포 클라우드 세션에서 돌아요. Claude Code의 프로젝트 스레드나 레포 여러 개를 붙인 세션에서는 레포의 훅이 돌지 않아요.

## 9. 하지 않는 것

- 열린 결정을 정하는 것
- `docs/spec/`, `docs/decisions/README.md`, `docs/harness-log.md`, `CLAUDE.md`, `.claude/`를 고치는 것 (훅이 막아요)
- master에 들어간 Flyway 마이그레이션을 고치는 것 (훅이 막아요)
- 테스트 기대값을 바꾸거나, 테스트를 지우거나 끄는 것
- master에 직접 push하는 것, 비밀값을 요청하거나 저장하는 것
- 단계 범위 밖을 고치는 것. 발견한 문제는 PR의 '그 밖에 발견한 것'에 적어요
- CI 워크플로를 약하게 만드는 것. 워크플로를 바꿨다면 '꼭 봐 주세요'로 표시해요
