## 배경

풀이 하나가 들어오면 사용자가 속한 스터디마다 어느 스터디 일에 셀지 정해요 (R4). 유예 안에 들어온 풀이는 전날이 '아직 판정 전, 판정 대상(쉬는 날·면제권 아님), 목표 미달'이면 전날로 가요. 이 확인과 반영 사이에 다른 일이 끼어들면 수가 틀려요.

1. **같은 사람의 풀이 두 개가 유예 안에 동시에 옴 (T7).** 목표 1인 멤버의 push 두 개가 00:05에 함께 오면 둘 다 '전날 0문제'를 보고 전날로 가서 전날 2, 오늘 0이 될 수 있어요. 맞는 결과는 전날 1, 오늘 1이에요 (5.5 '주의할 것').
2. **배정과 판정이 겹침 (T8, S12).** 판정 배치가 전날을 FAIL로 정하는 사이에 늦은 풀이가 전날로 가면 결과와 센 수가 어긋나요.
3. **같은 날 같은 문제 (R5, T4·T5).** 같은 문제를 두 번 커밋하거나 force push로 SHA가 바뀌면 풀이 기록이 둘이에요. 그 날에는 한 번만 세요.

스펙이 정한 것: 멤버 일 행을 `INSERT ... ON CONFLICT DO NOTHING` 다음 `SELECT ... FOR UPDATE`로 잠그고, 잠금 순서는 '전날 행 → 오늘 행'이에요 (5.5, S09 만들 것 2). 판정 배치도 같은 행을 잠가요 (5.10). 같은 날 같은 문제는 `study_day_solves`의 UNIQUE가 막아요 (data-model 4.3).

스펙이 정하지 않은 것: 사용자가 스터디 여러 개에 속하고(S09 만들 것 5) push 하나에 풀이가 여럿일 때(한 트랜잭션에서 배정을 여러 번 부름, S08) 스터디들에 걸친 잠금 순서. 부록 D `recordSolve`를 그대로 옮기면 스터디마다 '전날 잠금 → 결정 → 배정한 날 잠금' 순서라서, 잠그는 행이 배정 결과에 따라 달라지고 스터디에 걸쳐 순서가 섞여요. 이렇게 교착이 나요 (스터디 A·B, 목표 1, A의 전날은 미달·B의 전날은 달성):

| 순서 | tx1: 00:05 push, 문제 p1·p2 | tx2: 00:40 push (유예 밖), 문제 p3 |
|---|---|---|
| 1 | p1·A: (A, 전날) 잠금 → 전날로 | |
| 2 | p1·B: (B, 전날) 잠금 → 달성이라 (B, 오늘) 잠금 | |
| 3 | | p3·A: (A, 오늘) 잠금 |
| 4 | | p3·B: (B, 오늘) 대기 ← tx1 |
| 5 | p2·A: (A, 전날)은 이미 잡음 → 이제 달성이라 (A, 오늘) 대기 ← tx2 | |

PostgreSQL이 교착을 찾아 한쪽을 되돌리면 그 push는 수신함이 FAILED가 되고, P1에는 다시 처리하는 경로가 없어요 (D21, 재처리는 P2).

## 선택지

| 선택지 | 장점 | 단점 | 되돌리는 비용 |
|---|---|---|---|
| A. 멤버 일 행 비관적 잠금 + 전역 순서. 풀이 하나마다 잠글 행(후보 전날, 오늘)을 모든 스터디에 걸쳐 먼저 모으고, (스터디 일, 스터디 ID) 순서로 만들고 잠근 뒤 결정한다. 전날로 배정해도 오늘 행을 잠근다 | 스펙(5.5)의 방식 그대로이고 판정(S12)과 같은 행 잠금으로 맞물림. 잠그는 행이 배정 결과와 상관없이 정해져 교착이 없음. 잠금 범위가 한 사용자의 하루 이틀치라 다른 사람은 기다리지 않음 | 후보 전날이 있으면 오늘 행을 미리 만듦(센 수 0, 미판정. 오늘은 어차피 판정 대상이라 판정 배치가 만들 행). 한 트랜잭션의 풀이는 인정 시각이 같아야 순서가 지켜짐(지금 부르는 곳은 모두 그렇다) | 낮음 (코드만) |
| B. 낙관적 잠금(`version`) + 충돌 시 재시도 | 잠금 대기가 없음 | 행이 없을 때의 경합(INSERT)과 '전날로 갈지' 판단이 버전 하나로 안 잡힘. 재시도 코드가 웹훅 처리 안에 생김. 판정과의 경합(5.10)도 따로 맞춰야 함 | 중간 |
| C. 사용자 단위 직렬화: 배정 전에 `pg_advisory_xact_lock(user_id)`(또는 사용자 행 잠금) 하나를 잡음 | 교착 논리가 단순(잠금 하나) | 판정 배치는 사용자 잠금을 잡지 않아서 판정과의 경합은 여전히 멤버 일 행 잠금이 필요. advisory lock 키 관리, Supabase pooler에서의 동작 확인 필요 | 낮음 |
| D. SERIALIZABLE 격리 + 재시도 | 잠금이 코드에 드러나지 않음 | 직렬화 실패 재시도가 웹훅 처리 안에 생김. JPA·pooler에서 확인이 더 필요 | 중간 |
| E. 부록 D 순서 그대로 (스터디마다 전날 → 배정한 날) | 의사코드와 한 줄씩 같음 | 위 표의 교착 | 낮음 |

## 추천과 이유

**A.** 스펙이 정한 행 잠금을 그대로 쓰면서, '전날 행 → 오늘 행'을 스터디 여러 개에 걸친 전역 순서 (스터디 일, 스터디 ID)로 넓혀요. 잠그는 행 집합을 결정 전에 정하니(후보 전날 + 오늘) 순서가 배정 결과에 기대지 않아요.

- 한 push의 풀이는 인정 시각이 모두 같아요 (수신함의 수신 시각, S08). 그래서 첫 풀이가 필요한 행을 순서대로 모두 잡고, 나머지 풀이는 이미 잡은 행을 다시 잡아요. 트랜잭션마다 늘 오름차순으로만 잡으니 교착이 생기지 않아요.
- 판정 배치(S12)는 멤버마다 한 트랜잭션에서 행 하나만 잠가요 (5.10). 면제권(S11)은 멤버십 행 다음 멤버 일 행 하나를 잠가요 (5.7). 둘 다 이 순서와 부딪히지 않아요. S12가 한 트랜잭션에서 여러 날을 잠그게 되면 날짜 오름차순으로 잠가야 해요.
- 남는 경우 (추측, 재현 안 함): push 하나를 처리하는 트랜잭션 안에서 풀이 사이에 같은 사용자의 새 멤버십이 커밋되면(READ COMMITTED라 다음 풀이의 멤버십 조회에 보임), 둘째 풀이의 계획에 새 스터디의 오늘 행이 늦게 들어와요. 그 스터디 ID가 이미 잡은 같은 날 행의 스터디보다 작으면 순서가 깨지고, 그 사이 같은 사용자의 다른 push와 겹치면 교착이 날 수 있어요. 가입이 그 짧은 사이에 커밋되고 다른 push까지 겹쳐야 해서 지금은 막지 않았어요. 막으려면 트랜잭션마다 멤버십 목록을 한 번만 읽어 두면 돼요.
- 판정 대상 여부(가입·기수·쉬는 날)는 잠그기 전에 봐요. 이 값들은 지난 날에 대해 바뀌지 않아요 (R2 소급 없음, 기수 행의 시작일은 바뀌지 않음). 후보가 아닌 전날은 잠그지도 만들지도 않아요. 판정하지 않는 날에 빈 멤버 일 행이 생기지 않게 하려는 것이에요.
- 행은 엔티티 대신 네이티브 쿼리로 만들고 잠그고 고쳐요. open-in-view로 열려 있는 EntityManager의 엔티티는 잠가도 다시 채워지지 않기 때문이에요 (S07 PR #14 리뷰).
- 센 수는 넣은 뒤 `study_day_solves` 행 수로 다시 세요 (S09 만들 것 4). 더하기 대신 다시 세니 중복 배정이 있어도 맞아요.

C를 고르면 판정과의 경합에 행 잠금이 또 필요해 잠금이 두 종류가 돼요. B·D를 고르면 재시도 코드가 웹훅 처리 안에 들어와요.

## 근거

- 5.5 '만들 것'·'주의할 것', 5.10 '주의할 것', 부록 D `assignStudyDay`·`recordSolve`, data-model 4.3 `member_days`·`study_day_solves`
- [PostgreSQL 17 행 잠금](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS): `FOR UPDATE`끼리 기다리고, 같은 트랜잭션이 이미 잡은 행은 다시 잡아도 기다리지 않음. [교착](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-DEADLOCKS): "consistent order"로 잠그는 것이 가장 좋은 방어
- [PostgreSQL 17 INSERT ON CONFLICT](https://www.postgresql.org/docs/17/sql-insert.html#SQL-ON-CONFLICT): 동시에 같은 키를 넣으면 나중 트랜잭션이 앞 트랜잭션을 기다린 뒤 아무것도 하지 않음
- 구현: `progress.AssignmentPlan`(계획·결정), `progress.MemberDayKey#LOCK_ORDER`, `progress.StudyDayAssigner`, `progress.persistence.MemberDayRepository`(`insertIfAbsent`, `lock`, `recountSolved`), `study.MemberStudies`
