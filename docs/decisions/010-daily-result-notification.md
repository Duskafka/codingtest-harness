## 배경

판정 배치가 하루치 판정을 마치면 그날 결과를 디스코드나 방장 웹 푸시로 알려요 (5.8 표 `DAILY_RESULT`, 시점 '판정 직후', 키 `DAILY_RESULT:{study}:{day}`). 부록 D(pseudocode '판정 배치')는 진행 지점을 올린 뒤 `createNotification(DAILY_RESULT, study, day)`를 직접 불러요.

제약은 이래요.

- **모듈 방향:** judgment → notification 화살표가 없어요. notification → judgment도 없어요. notification은 progress·study만 써요 (4.2, ArchUnit `ModuleRules`).
- **반대 방향 통지:** 4.2는 '커밋 뒤 이벤트'로 하라고 하면서, 이벤트가 사라져도 DB로 다시 맞출 수 있어야 한다고 해요. S13 PR 반영 뒤 4.2는 'outbox 행을 넣는 통지는 발행한 트랜잭션 안의 리스너가 같은 트랜잭션에서 넣을 수 있다'고도 해요 (알려진 충돌 5번, `RULE_CHANGED`). 판정 결과 알림은 이 결정 제안서에서 정하기로 했어요 (사람이 정함, 2026-11-28).
- **수용 기준:** 판정 배치를 두 번 돌려도 하루에 하나, 판정 뒤 서버가 죽어 이벤트가 사라져도 결국 만들어진다.
- **지금 코드:** 진행 지점(`studies.last_judged_day`)은 study의 `JudgingDays#markJudged`가 따로 짧은 트랜잭션에서 조건부 UPDATE로 올려요(앞으로만, 이미 올라갔으면 0행). 멤버 판정은 그 전에 멤버마다 트랜잭션으로 끝나 있어요 (결정 008). 판정 배치는 이벤트를 하나도 발행하지 않아요.

## 선택지

| 선택지 | 장점 | 단점 | 되돌리는 비용 |
|---|---|---|---|
| A. 같은 트랜잭션 리스너: study `JudgingDays#markJudged`가 진행 지점을 실제로 올렸을 때 같은 트랜잭션에서 'study 하루 판정 끝' 이벤트를 발행하고, notification 리스너(동기 `@EventListener`, `MANDATORY`)가 그 트랜잭션에서 outbox 행을 넣음 | 진행 지점과 알림 행이 함께 커밋되거나 함께 롤백돼 사라질 틈이 없음. 새 컬럼·스케줄러 없음. 판정 직후. `RULE_CHANGED`와 같은 방식이라 코드가 하나의 모양. judgment는 notification을 모르고(이벤트 타입은 study에 있음), ArchUnit 규칙을 바꾸지 않음 | 행 넣기가 실패하면 진행 지점도 올라가지 않아 그 스터디의 판정 배치가 다음 실행까지 그날에서 멈춤(멤버 결과는 이미 저장, 다음 실행이 건너뛰고 다시 진행 지점을 올리려 함). 진행 지점 트랜잭션에 알림 내용 조회(그날 결과 수)가 더해짐 | 낮음: 리스너와 이벤트 발행 한 곳 |
| B. 별도 진행 지점 + 알림 스케줄러: `studies`에 '결과 알림을 만든 날' 컬럼을 두고 notification 스케줄러(1분, ShedLock)가 `last_judged_day`까지 따라가며 행을 만듦 (`last_reminded_day`와 같은 모양) | 알림 쪽 문제가 판정을 막지 않음. 4.2의 'DB가 진실의 원천' 그대로 | 컬럼(마이그레이션)·스케줄러·스레드가 늘고, 기존 스터디의 시작값(배포 때 `last_judged_day`로)이 필요. 최대 1분 늦음. 진행 지점이 둘이라 어긋나면 맞출 규칙이 더 필요 | 중간: 컬럼 |
| C. 커밋 뒤 이벤트 + 따라잡기 배치 (4.2 원래 문구): `AFTER_COMMIT` 이벤트로 바로 만들고, 사라진 것은 B의 배치가 다시 맞춤 | 판정을 막지 않으면서 바로 보냄 | 경로가 둘이라 코드·테스트가 가장 많음. B의 컬럼·스케줄러도 필요 | 중간 |

## 추천과 이유

**A**예요.

- 수용 기준 '이벤트가 사라져도 결국 만들어진다'를 구조로 지켜요. 이벤트를 커밋 뒤가 아니라 진행 지점을 올리는 트랜잭션 안에서 받으니, 진행 지점이 올라갔다면 알림 행도 있어요. 서버가 그 트랜잭션 도중에 죽으면 둘 다 없고, 다음 실행이 그날부터 다시 해요 (멤버 판정은 결과가 있어 건너뜀, 결정 008). 그래서 '다시 맞출 배치'가 필요 없어요.
- '하루에 하나'는 두 겹으로 지켜요. 진행 지점 UPDATE가 실제로 1행을 바꾼 트랜잭션에서만 발행하고(두 실행이 겹쳐도 한쪽만 올림), 키 `DAILY_RESULT:{study}:{day}`가 UNIQUE라 `ON CONFLICT DO NOTHING`이 마지막 방어선이에요.
- S13에서 사람이 `RULE_CHANGED`에 같은 방식을 골랐고(2026-11-27), 4.2에 반영됐어요. 같은 문제(알려진 충돌 2번·5번)를 같은 모양으로 풀면 읽는 사람이 한 가지만 알면 돼요.
- 단점(행 넣기 실패 = 진행 지점 정지)은 행 넣기가 `INSERT … ON CONFLICT DO NOTHING` 한 문장과 그날 결과 수를 세는 조회 하나라 드물다고 봐요. 멈춰도 멤버 결과는 이미 저장돼 있고, 다음 5분 실행이 다시 시도해요. 판정 배치가 이 실패를 오류로 세고 그 스터디만 멈추게 해야 판정 배치의 오류 지표(`studybot.judgment.errors`)와 로그에 남고 다른 스터디 판정이 이어져요 (아래 'A의 세부'의 judgment 변경).

B를 고르면 알림 문제가 판정을 막지 않는 대신 진행 지점이 둘이 되고 컬럼이 생겨요. C는 B에 이벤트 경로를 더한 것이라 P1에는 과해요.

**A의 세부 (S14 구현):**

- 이벤트는 study 루트 패키지의 레코드예요 (`StudyDayJudged`: 스터디 ID·이름·모드·방장, 판정한 날, 그다음 스터디 일이 끝나는 시각). judgment는 notification을 부르지 않아요.
- judgment는 한 곳만 바꿔요. 지금 판정 배치는 `markJudged`의 예외를 잡지 않아서, 결과 알림 행 넣기가 실패하면 `run()`의 남은 스터디 판정까지 멈추고 오류 지표도 오르지 않아요. 그래서 `markJudged` 예외를 오류로 세고 그 스터디만 멈추게 해요 (5.10 처리 순서 3의 오류 격리). 판정 규칙·순서는 그대로예요. (제안을 처음 쓸 때는 'judgment 코드는 바꾸지 않아요'라고 적었는데 구현하며 이 빈 곳을 찾아 고쳤어요. S14 PR 판단 기록 '꼭 봐 주세요')
- 리스너의 결과 수 조회는 그날 멤버 일 행만 읽어요. 현황 맥락 조회의 날짜 검사가 진행 지점 트랜잭션 안에서 던져 판정을 막지 않게 하려는 거예요.
- 리스너(notification)는 그날 판정 결과를 progress 공개 조회로 세서, 성공·실패·면제권 결과가 하나도 없으면(쉬는 날뿐, 판정 대상 없음) 만들지 않아요.
- 채널은 그 스터디의 디스코드가 켜져 있으면 디스코드, 아니면 방장 웹 푸시예요 (5.8 표 '채널 또는 방장'). 행은 하나예요.
- 만료는 판정한 날 다음 스터디 일이 끝나는 시각이에요. 오래 꺼졌다 따라잡는 날처럼 이미 지났으면 만들지 않아요 (5.8 '마감이 지난 날은 만들지 않아요'와 같은 생각). 건너뛰는 날·채널·만료는 S14 PR 판단 기록이에요.

## 근거

- Spring Framework 7.0 참조 문서 'Standard and Custom Events': 리스너는 기본으로 동기 실행이고 `publishEvent()`는 리스너가 끝날 때까지 기다리며, 발행한 쪽 트랜잭션이 있으면 그 안에서 돈다. https://docs.spring.io/spring-framework/reference/core/beans/context-introduction.html#context-functionality-events
- 같은 문서 'Transaction-bound Events' (`@TransactionalEventListener`, `AFTER_COMMIT`): C의 커밋 뒤 이벤트는 커밋 뒤 서버가 죽으면 사라진다. https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html
- 스펙: 4.2(반대 방향 통지, 진실의 원천), 알려진 충돌 2·5번, 5.8 '알림 종류'·'주의할 것'(중복 생성 금지 + 적어도 한 번), 5.10 처리 순서 3, 결정 008(멤버마다 트랜잭션, 하루치가 끝나야 진행 지점)
- 선례: S13 `RuleChangeNotifier`(`StudyRulesChanged`를 같은 트랜잭션에서 받음, PR #35)
- 추측: 운영에서 행 넣기가 실패해 진행 지점이 멈추는 일이 얼마나 드문지는 아직 데이터가 없어요.

## 검증 방법

- S14 테스트 `DailyResultIntegrationTest`
    - 판정 배치를 두 번 돌려도 `DAILY_RESULT` 행은 하나
    - 테스트 트리거로 결과 알림 INSERT를 실패시키면 멤버 결과는 저장되고 진행 지점은 그대로, 알림 행은 없음 → 트리거를 지우고 다시 돌리면 행이 생기고 진행 지점이 올라감
    - 디스코드 켜짐 → 디스코드 행, 꺼짐·혼자 쓰기 → 방장 웹 푸시, 쉬는 날·지난 날은 만들지 않음
- 운영: `studybot.notification.created{type=DAILY_RESULT}`와 판정 배치의 `studybot.judgment.days`를 비교하고, `studybot.judgment.errors`가 늘면 로그에서 결과 알림 쪽 실패인지 봐요.
